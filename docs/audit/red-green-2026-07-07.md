### Back-then-Next after card save re-confirms a consumed SetupIntent — user permanently trapped, funnel shows rx_card_saved with no rx_submitted
**File:** `website/src/pages/rx/leaky-gut/questionnaire.astro`  
**What:** confirmStripeCard() (leaky-gut:456, weight-loss:440, testosterone-ed:480, peptides:389, regenerative-medicine:411) has no 'already saved' guard (e.g. `if (paymentMethodId) return true;`). The Next handler then does `currentStep--; return;` so the user is bounced back to the card step with an error and can NEVER reach the review/submit step again (the same consumed clientSecret is retried forever — initStripeCard also early-returns because cardElement is already set, so a fresh SetupIntent is never created). Same code in all 5 questionnaires.
**Failure:** Real customer on /rx/weight-loss/questionnaire enters card on step 5, Next → card saved (rx_card_saved fires), lands on step 6 review, notices a typo, clicks Back to any earlier step, then Next again through step 5→6: confirmCardSetup errors, currentStep bounces to 5, and every subsequent attempt fails. Lost live-Stripe sale; PostHog funnel records rx_card_saved but no rx_submitted, misread as voluntary review-step drop-off when it is a bug trap.
**Verifier:** high — page refresh fully recovers (fresh SetupIntent + new payload), so 'permanently trapped' overstates it; still loses live sales and corrupts the PostHog funnel, so high rather than critical.

### patient-record-intake is unauthenticated and overwrites any patient's PHI record with no ownership check
**File:** `lambdas/patient-record-intake/src/handler.ts`  
**What:** The handler performs no auth (no JWT/authorizer check, no verified session) and derives the partition key purely from the request-body email: contactId = deriveContactId(email). Write 1 is a PutCommand on {contactId, sk: RECORD_SK} with NO ConditionExpression, so it unconditionally overwrites the root PatientRecord — demographics, history (medications/allergies/conditions/height/weight), screeningAnswers, and cardOnFile — for whatever email the attacker supplies. contactId is a deterministic hash of the lowercased email (namespace is a hardcoded constant, and the derivation is shared client-side), so any attacker who knows a victim's email can target their record. A provider then reviews falsified allergies/medications/conditions in the exported clinical packet. It also lets an attacker inject unlimited bogus encounters (state:'new') into the clinical queue and fire coordinator-notify emails. Fix: require an authenticated identity, derive contactId from the verified session (not body email), and use a create-or-owner condition instead of blind Put.
**Failure:** Attacker sends POST /patient-record-intake {email:'victim@example.com', history:{allergies:[], medications:[], conditions:['none']}} → victim's real allergy/medication history is silently overwritten with empty/false data; provider prescribes against a record showing 'no allergies,' a direct patient-safety failure.
**Verifier:** keep critical — unauthenticated overwrite of existing patients' medication/allergy history in a live system whose records feed provider-reviewed clinical packets is a direct patient-safety and HIPAA-integrity failure; attack cost is one HTTP POST with the victim's email.
